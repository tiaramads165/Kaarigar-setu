# Kaarigar Setu STRIDE Threat Model

Scope: the Java web application, the Python ML service, PostgreSQL, the TLS proxy and the moderator console. Trust boundaries: browser / console to
proxy (untrusted internet), proxy to Tomcat, Tomcat to the ML service (shared secret), Tomcat to Postgres (restricted role). "Evidence" names the tests or
checks that would fail if the mitigation were removed (`docs/TEST_REPORT.md`).

## Threats and mitigations

| # | Category | Threat | Mitigation | Evidence |
|---|---|---|---|---|
| S1 | Spoofing | Someone logs in as another worker or employer | Phone + OTP (6 digits, PBKDF2 + pepper, 5 attempts, 5 min, single use, bound to role and phone); new session id on login; rate limits | `OtpServiceTest`, `AuthServiceTest`, `SessionsTest`, e2e s.3-4 |
| S2 | Spoofing | A person claims to be an employer to vouch for a worker | Attestation OTP goes to the **employer's own** registered phone as step-up; self-attestation refused; one live attestation per pair | `AttestationWorkflowServiceTest`, e2e s.6 |
| S3 | Spoofing | Moderator account takeover | Password (PBKDF2, 210 000 iterations) **and** OTP; per-user and per-IP limits; constant-time compare; dummy hash so unknown names cost the same | `AuthServiceTest`, e2e s.9 |
| S4 | Spoofing | A caller impersonates the Java app to the ML service | `X-Internal-Token` shared secret (constant-time); ML service on an internal network only; refuses to run without a token in prod | ML `test_transcribe_and_security.py`, `MlServiceClientTest` |
| T1 | Tampering | A credential's score is edited, or one is forged with the attacker's own key | RSA-3072 (min 2048) SHA-256 signature over an RFC 8785 canonical form (any JSON library can rebuild the signed bytes); verification re-checks signature, key id, revocation and expiry server-side; a stranger can verify offline with `scripts/verify_credential.py`; a signed revocation list; key rotation keeps old credentials valid | `CanonicalJsonTest`, `SignatureKeyRotationTest`, `CredentialServiceTest`, e2e s.7, attack harness CRED-01 to CRED-06 |
| T2 | Tampering | SQL injection | PreparedStatement only; source guard; fuzz over every DAO method | `NoStringBuiltSqlTest`, `DaoSqlInjectionFuzzTest` |
| T3 | Tampering | Cross-site request forgery | CSRF token header on every POST + Origin check; session cookie `SameSite=Strict`; JSON content type required | `CsrfFilterTest`, e2e s.3 |
| T4 | Tampering | A fooled or compromised LLM / ML service returns an inflated or malformed score | Transcript fenced with a nonce; strict schema; marks clamped and totals recomputed by us; Java re-validates every response; unreliable output = zero + human review | ML `test_evaluate.py`, `MlServiceClientTest` |
| T5 | Tampering | The audit trail is edited, truncated or rolled back to hide an action | DB triggers block UPDATE/DELETE/TRUNCATE; hash chain in the DB and an HMAC-keyed file chain with a head file; the newest file line is **anchored in the database** every 25 events and every 5 minutes, so even a consistent older log+head pair (a rollback) is caught; offline verifier `AuditVerifyCli --db`; verifier endpoint and console button | `ChainedAuditFileSinkTest`, `AuditLoggerTest`, `PipelineDaoIntegrationTest.auditLogIsAppendOnlyAndHashChained`, attack harness AUD-01, AUD-02 |
| T6 | Tampering | A poisoned model file (pickle) executes code | SHA-256 digest checked before `joblib.load`; missing digest/model is an error in prod | ML `test_a_tampered_model_file_is_refused` |
| T7 | Tampering | Fake endorsements inflate trust (collusion, rings, bursts, Sybil accounts) | Isolation Forest on IP/device frequency, gap, reciprocity (flags crude rings, **misses patient ones**: measured); flagged = human review; PageRank with recency decay and anomaly discount; three independent employers for full confidence; **the Excellent band needs an employer a moderator has vetted**, because three throwaway accounts used to be enough (measured) | `TrustAttackSimulationTest`, `ReputationScoringTest`, `TrustScoreServiceTest`, `docs/FRAUD_ATTACK_SIMULATION.md`, e2e s.8 and 9b, attack harness FRAUD-01 |
| R1 | Repudiation | A user or moderator later denies an action | Every security-relevant event audited (ids only) in two tamper-evident stores | all `AuditLogger` call sites; e2e audit check |
| R2 | Repudiation | Moderator decisions and vettings cannot be attributed to a person | **Mitigated** (migration 008): every moderator is a named account with their own password and their own phone for the sign-in code; every action is audited under that person's name; vetting and dispute rulings are proposed by one and approved by a different one, and the record names both. Residual: accounts are made by an operator, so the operator is trusted; an operator or both moderators colluding defeats it | `docs/SECURITY_RUNBOOK.md` (moderator accounts), `ModeratorApprovalIntegrationTest`, harness ACL-09 and AUTH-11 |
| R3 | Repudiation / tampering | An employer posts a rating about a worker who never agreed to it (including a bad one); the worker cannot dispute it | **Mitigated** (migration 006): the code still goes to the employer's phone, so the employer can still post it, but the worker now sees every confirmation about them and may **accept** it (a record) or **dispute** it with a reason. A dispute holds the confirmation out of the trust score, the credential, the passport count and the employer's record until a moderator rules UPHELD (counts again) or REMOVED (never counts). Acceptance is optional on purpose: if it were required a worker could refuse every bad rating and own their score. Limits: a 30-day window and at most 3 open disputes, enforced under a row lock (a race found by harness FRAUD-02 let 4 of 6 through before the lock). Residual: a worker who never looks, or looks after the window, is not protected; up to 3 bad ratings can be hidden until a moderator rules | `docs/FRAUD_ATTACK_SIMULATION.md` s.5 |
| I1 | Information disclosure | Phone numbers leak from the database, logs or credentials | AES-GCM + HMAC lookup key; masked in logs; credentials use a random pseudonymous subject; audit log has no phone-shaped values | `PhoneProtectorTest`, `AuditLoggerTest`, `CredentialServiceTest`, e2e |
| I2 | Information disclosure | Account enumeration | Identical responses and codes for known and unknown numbers; errors carry a code, never exception text | `AuthServiceTest`, e2e s.4 |
| I3 | Information disclosure | Another worker's credential or data is read | Owner checks answer 404; deny-by-default role filter | `AuthFilterTest`, e2e s.7 |
| I4 | Information disclosure | Raw voice data retained | Audio held in memory only and zeroed after transcription | `AssessmentPipelineServiceTest` |
| I5 | Information disclosure | Grader-only rubric content (criteria, keywords) leaks to workers | The rubric endpoint and the start response expose only question text and max marks | ML `test_rubric_route_never_leaks_grader_only_content`, e2e s.5 |
| I6 | Information disclosure | XSS steals a session | `c:out` everywhere, no scriptlets, no inline script, strict CSP, `HttpOnly` cookie | `XssGuardTest`, e2e s.1 |
| I7 | Information disclosure | Traffic or cookies over plain HTTP | TLS terminated at the proxy, HSTS, `Secure` cookie; **configuration only, not exercised without Docker** | `docker/caddy/Caddyfile`, `AppSettings.validate` |
| I8 | Information disclosure | A copy of the database, a backup or the audit file is stolen (a disk, a dump, a misconfigured bucket) | Transcripts, feedback, scores, ratings, job details, names, dispute reasons, fraud features, signed credential payloads and the details of audit events are stored as AES-256-GCM ciphertext written by the application (migration 010); the audit FILE is encrypted line by line, with its hash chain computed over the plaintext so it still verifies and its database anchors still match; credential export files are encrypted; each value is bound to its column and row, so a ciphertext cannot be moved to another place; the keys (`DATA_ENC_KEYS`, one derived key per use) are in the environment, never in the database or the data directory; `scripts/seal-at-rest.sh` converts old data, re-keys, and checks that nothing is plain. **Residual:** the application holds the key, so an attacker who controls the running server or reads its environment reads everything; event type, actor and time of audit events, ids, statuses, timestamps, trade, language and the anomaly score stay plain on purpose; audit-table rows written before encryption stay plain because the table is append-only; transcripts are sent to the ML service in the clear inside the host | `DataCipherTest`, `EncryptionAtRestIntegrationTest`, `ChainedAuditFileSinkTest`, `ModeratorWriteAccessTest`, harness DATA-06, DATA-07, AUD-01, AUD-02 |
| D1 | Denial of service | OTP guessing or SMS flooding | Per-address, per-phone and per-user limits; 5-attempt lockout of a code. **Mitigated for returning users** (migration 009): the budgets that belong to a phone number used to be shared by everyone who typed it, so a stranger could use up the victim's request quota or lock the victim's pending code. A browser that has signed in is now a trusted device with its own budget and its own code; every code is bound to the browser that asked for it; unknown devices must solve a proof-of-work puzzle first and share a per-phone-and-address budget plus a per-phone hourly ceiling of 12. **Residual:** an attacker who pays the puzzle from several addresses can use up the ceiling and delay a victim signing in from a brand-new device for up to an hour | `RateLimiterTest`, `OtpServiceTest`, e2e s.4, attack harness AUTH-01, AUTH-07, AUTH-08, AUTH-12 to AUTH-15, `AuthServiceTest`, `ProofOfWorkTest` |
| D6 | Denial of service / disclosure | Sign-up flooding, finding out which numbers are registered (409 on duplicates), flooding public verification | Per-address throttles on registration (20 per 10 min) and on public verification, QR and key endpoints (120 per minute) | attack harness AUTH-10, DATA-05 |
| D2 | Denial of service | Oversized or malformed uploads | Hard byte cap before buffering; WAV header, duration and channel validation; body size limits at the proxy and Tomcat | `WavValidatorTest`, e2e s.5 |
| D3 | Denial of service | The ML service goes down | Fail safe: attestations go to human review, nothing is auto-approved; assessment returns 503 | `AttestationWorkflowServiceTest` |
| D4 | Denial of service | Slow-loris / exhausting the DB pool | Connection timeout and header limits in `server.xml`; pooled connections with a size cap | hardened Tomcat run |
| S5 | Spoofing | Someone shows another worker's credential as their own (screenshot or forwarded QR) | The QR is a fixed link, so this cannot be prevented, only made visible: the worker's signed-in session can mint a **live code** (HMAC, bound to one credential, stops counting as live after 5 minutes) and the verification page says "shown live", "not live" or "static link" | `PresentationTokensTest`, e2e s.7, attack harness CRED-07 |
| S6 | Spoofing | A good recording of an answer (the worker's own, an expert's, one taken from another account, or text-to-speech reading a stolen transcript) is played into the assessment | **Mitigated, with residuals** (migration 011, [`REPLAY_DETECTION.md`](REPLAY_DETECTION.md)): (1) a spoken code made when the question is shown must be said inside the answer, so a recording made earlier cannot contain it; (2) every recording is fingerprinted (keyed hashes of acoustic landmarks) and compared with every earlier answer of every worker: the same recording is found through noise, a different volume, a narrower band, another sample rate, a trimmed start or a speaker-to-microphone hop; (3) the transcript's word trigrams are compared the same way, which finds a time-stretched or re-voiced copy; a match gives no score, holds the answer for review and blocks the credential; a check that cannot run is held too. Measured on real speech and real Whisper; negatives share at most 4 landmarks, replays 100 or more | `ReplayDetectorTest`, `ReplayChallengeTest`, `ReplayDefencesPipelineTest`, `ReplayDaoIntegrationTest`, ML `test_audio_fingerprint.py`, e2e s.5a, harness REPLAY-01..06 |
| M1 | Detection | An attack is under way and nobody notices | CSRF rejections, role violations and rate-limit hits are audited (once per client per minute, so an attacker cannot flood the log); the moderator console's Security tab shows counts, threshold alerts and the audit-trail integrity | `SecurityMonitorTest`, `PipelineDaoIntegrationTest`, e2e s.9 |
| E1 | Elevation of privilege | A worker reaches moderator or employer routes | Role per route, deny by default; employer routes explicitly employer-only | `AuthFilterTest`, e2e s.3 |
| E2 | Elevation of privilege | A compromised app account damages data | Restricted DB role: DML only, DELETE on three tables, no DDL, audit log append-only; containers non-root, read-only, capabilities dropped | `database/setup_roles.sql`, e2e s.10 |
| E3 | Elevation of privilege | Vulnerable dependencies | Pins, `pip-audit` + OSV in CI; Tomcat/pgjdbc/starlette/python-multipart upgraded after real findings | CI `dependency-scan`, `docs/TEST_REPORT.md` s.6 |

## Residual risks (accepted or open)

1. **OTP offline brute force**: a 6-digit code has 10^6 values; if the database leaks without the pepper they could be recovered within the 5-minute window only (they expire and lock). Keep `OTP_PEPPER` out of the database.
2. **OTP delivery**: only a console sender exists; codes are in the server log. Treat the log as sensitive until an SMS sender is added.
3. **Two moderators who collude, or an operator with database-owner rights** (R2): the two-person rule stops one stolen or fooled login; it does not stop two people, or the person who creates the accounts. Accounts are created only with the database owner's credentials, never through the application.
4. **The database owner can disable the audit triggers**; the application never uses that account, and the chain still reveals any edit afterwards.
5. **In-memory rate limiting is per node**; run one app instance, or move the limiter to the database/Redis before scaling out.
6. **Key loss**: losing the signing keystore invalidates every issued credential; losing `PHONE_ENC_KEY` makes phone numbers unrecoverable. Back both up separately from the data.
7. **Synthetic fraud data and a TEST ONLY rubric**: the ML results do not describe real-world accuracy.
8. **Docker and TLS proxy untested**; see `docs/TEST_REPORT.md` section 5.
9. **Insider or fooled moderator vets a fake employer** (T7): the vetting rule moves the attack from "register accounts" to "corrupt a person"; with named accounts and two-person approval, one fooled or dishonest moderator can no longer vet alone: a second, different moderator has to approve, and both names are in the audit trail.
10. **SIM farms** reach the Good band (up to 79.99) with three fake employers each holding a phone number.
11. **The development Tomcat started by `cargo` shows its default error page (with the version) for requests it rejects before the application sees them**; the production `docker/tomcat/server.xml` turns this off. Found by attack harness INJ-02.
12. **`TRUST_FORWARDED_FOR=true` is set for local development** so tests can simulate many clients; with it, a directly reachable app lets a caller choose the address used by per-address limits (per-phone, per-username and per-code limits still hold, see AUTH-07). It must be off unless a proxy overwrites the header.
13. **Audit appends re-read the whole file** (O(n) per write): fine for a pilot, replace before large volumes.
14. **Static analysis and the attack harness check this code, not a deployment**: ZAP (dynamic scan), Trivy and the Docker path run only in CI.
15. **Replay detection finds RE-USE, not cheating** (S6): a person who records a fresh, original answer (or reads a prepared script aloud) and says the live code is accepted, as is an answer given with a helper standing by or a live text-to-speech of an original script. There is no speaker verification or anti-spoofing model. The audio check does not survive a change of speed (the word check covers it for answers of 14 or more word trigrams). Calibrated on synthesised speech and its recognition, not on real phone recordings. There is no review queue for held answers yet (the worker retakes). The employer-confirmed trust score is the control for the rest.

## Deployment requirement

Tomcat must only be reachable through a TLS-terminating proxy (the compose file does this). The `Secure` cookie setting intentionally keeps session cookies off plain HTTP, and
`TRUST_FORWARDED_FOR=true` is only safe when the proxy overwrites `X-Forwarded-For`.
